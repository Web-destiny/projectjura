# Публикация ДЖУРЫ

Приложение статическое. Для MVP достаточно обычного виртуального хостинга с HTTPS и настройкой SPA fallback. Покупка VPS, базы данных и Node-процесса на сервере не требуется.

## 1. Проверить релиз локально

```sh
npm ci
npm run typecheck
npm run lint
npm test
npm run build
npm run test:e2e
npm run preview
```

Для E2E предварительно выполните `npx playwright install chromium`. В PowerShell вместо `npm`/`npx` можно использовать `npm.cmd`/`npx.cmd`.

В `dist` находятся `index.html`, хэшированные JS/CSS/worker/fonts в `assets`, favicon, manifest, robots и конфигурационные файлы. Загружать нужно **содержимое** `dist`, включая скрытый `.htaccess`. Исходники, `node_modules`, fixtures и `.env` на хостинг не отправляются.

## 2. Разместить на российском хостинге

Подойдёт виртуальный хостинг, позволяющий обслуживать статические файлы, включить HTTPS, задать HTTP-заголовки и перенаправлять неизвестные маршруты на `index.html`. Например, можно использовать Timeweb; конкретный тариф и условия проверьте перед оплатой. ДЖУРА не требует PHP или базы данных.

1. Создайте сайт в панели выбранного хостинга и укажите домен/поддомен.
2. Откройте файловый менеджер или SFTP и найдите document root этого сайта (имя каталога зависит от хостинга).
3. Загрузите туда файлы из `dist`. Не меняйте файлы чужих сайтов.
4. Для Apache используется приложенный `.htaccess` (нужны `mod_rewrite`, `mod_headers` и разрешённый AllowOverride). Если перед Apache стоит Nginx, проверьте, что он не перехватывает неизвестные маршруты и что заголовки добавляются также к JS worker.
5. Для Nginx перенесите настройки `deploy/nginx.conf`, заменив `root` и `server_name`. Подключите `deploy/security-headers.conf` из указанного пути или скорректируйте include.
6. Если панель не позволяет редактировать конфигурацию, передайте поддержке требование: `/create`, `/edit`, `/templates`, `/guide` должны отдавать `index.html`; существующие `/assets/*` — реальные файлы, отсутствующие assets — HTTP 404.

`_headers` и `_redirects` понимают некоторые платформы статического хостинга. Обычный Apache/Nginx их сам не применит. Проверяйте именно HTTP-ответы.

Документация панели: [параметры сайта Timeweb](https://timeweb.com/ru/docs/virtualnyj-hosting/rabota-s-sajtom/nastrojki-sajta-na-hostinge/). Конфигурация fallback основана на [Nginx try_files](https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files).

## 3. Подключить домен и DNS

Получите IP или целевое имя у хостинга, не подставляйте произвольный адрес.

| Имя   | Тип   | Значение                                        |
| ----- | ----- | ----------------------------------------------- |
| `@`   | A     | IPv4 вашего хостинга                            |
| `www` | CNAME | основной домен, если это поддерживает провайдер |
| `@`   | AAAA  | только если хостинг сообщил рабочий IPv6        |

Для поддомена, например `app`, задайте его A/CNAME по инструкции провайдера. Не заменяйте MX/TXT существующей почты. Если выбран перенос NS на хостинг, заранее перенесите все действующие DNS-записи. A-запись и смена NS — альтернативные способы управления, делать оба вслепую не нужно.

Дождитесь обновления DNS с учётом TTL. Проверьте `nslookup ваш-домен.ru`, затем откройте сайт. Изменение протокола, домена или браузера создаёт другой origin: локальные шаблоны со старого адреса не появятся автоматически, их переносит `.dzhura`.

## 4. Включить HTTPS

Выпустите сертификат в панели хостинга для основного имени и `www`, если используете оба. Проверьте DNS и автоматическое продление. После установки включите редирект HTTP → HTTPS и выберите один канонический адрес.

Порядок в Timeweb: [заказ и установка SSL](https://timeweb.com/ru/docs/ssl-sertifikaty/zakaz-ustanovka-i-prodlenie-ssl/). Наличие бесплатного сертификата и его условия уточняйте в текущем тарифе.

HSTS включайте только после проверки HTTPS и всех нужных поддоменов. В шаблон намеренно не включён `includeSubDomains`: его нельзя безопасно назначать чужим поддоменам автоматически.

## 5. Проверить production

- Откройте `/`, прямые `/create` и `/guide`, обновите страницу. Неизвестный маршрут показывает экран 404 приложения (SPA отвечает 200).
- В DevTools → Network проверьте MIME JavaScript, worker и шрифтов; без внешних CDN и загрузок пользовательских файлов.
- Проверьте заголовки основного HTML **и файла worker**: CSP, `nosniff`, Referrer-Policy. CSP worker берётся из ответа самого worker; policy страницы не заменяет её.
- Политика включает `connect-src 'none'`, `worker-src 'self'`, `object-src 'none'`. Inline CSS разрешён для стилей DOCX; inline JS и eval не разрешены. Не добавляйте аналитику или сторонние скрипты без пересмотра модели приватности.
- Хэшированные assets: `Cache-Control: public, max-age=31536000, immutable`. `index.html`: `no-cache`. Если отсутствующий JS возвращает HTML, исправьте fallback.
- Пройдите создание одного DOCX, XLSX → ZIP, визуальное поле, поиск/замену, локальный шаблон, `.dzhura`, перезагрузку черновика и отмену большой пачки.
- Скачайте DOCX, откройте в вашей версии Word/LibreOffice, сравните таблицы, колонтитулы, стили и переносы.

Проверка CSP: [MDN worker-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/worker-src) и [Content-Security-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy).

## 6. Новая версия и откат

1. Сохраните предыдущий комплект production-файлов.
2. Соберите и проверьте новую версию с `npm ci` и lock-файлом.
3. Сначала загрузите новые assets, затем замените `index.html` и остальные корневые файлы. Ещё лучше — каталог релиза и атомарное переключение document root, если панель поддерживает.
4. Не удаляйте assets предыдущей версии сразу: открытая вкладка может позже запросить ленивый модуль.
5. Проверьте прямые маршруты и основные сценарии. При проблеме верните предыдущий index/комплект.

Релиз не требует сброса IndexedDB. При будущих изменениях схемы БД нужны явные миграции, без удаления данных пользователя.

## Альтернатива: Docker + Nginx

```sh
docker build -t dzhura:1 .
docker run --rm -p 8080:80 --name dzhura dzhura:1
```

Откройте http://localhost:8080. На сервере HTTPS завершайте в управляемом reverse proxy/панели. Контейнер обслуживает только статику; томов с пользовательскими документами нет. Kubernetes, серверная БД и Go-сервис не требуются.

Сам контейнер и конфигурацию Nginx необходимо проверить на целевом сервере (`nginx -t`, HTTP-заголовки, HTTPS и маршруты). Локальные браузерные тесты не доказывают корректность DNS, сертификата и конфигурации чужого хостинга.

## Следующий практический шаг

Выбрать уже имеющийся или новый российский хостинг и домен. После получения данных панели можно последовательно загрузить `dist`, настроить fallback, DNS и HTTPS и повторить checklist. Секреты и пароли не вставляйте в исходники; используйте SFTP/панель и штатный менеджер секретов.
